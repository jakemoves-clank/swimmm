# Deployment notes

Launch checklist for running Swimmm publicly. Human-scale site (<100 uses/day),
free to host, zero tolerance for high-volume abuse.

## Mapbox token (do this before launch)

The `PUBLIC_MAPBOX_TOKEN` ships to every browser and **will** be scraped.
In the Mapbox dashboard:

1. **URL-restrict** the production token to your domain. Use a separate,
   localhost-restricted token for development.
2. Keep the account card-less, or set a spending cap + usage alerts.
3. Rotate the token if usage ever looks wrong.

## Environment

- `PUBLIC_MAPBOX_TOKEN` — the URL-restricted token
- `ORIGIN` — the site's public URL (adapter-node requirement)
- `BODY_SIZE_LIMIT=65536` — no POST routes exist; keep it small anyway
- `DB_PATH` — put it on a **persistent volume** so redeploys don't re-download
  city data (the refresher's state lives in the DB)

## Runtime

- Run the node process as a non-root user.
- Never expose `vite dev` or the vitest UI publicly (known vulnerabilities are
  confined to those dev tools; `npm audit --omit=dev` is clean).
- Single instance only — multiple instances would each refresh from the city
  independently. This site should never need more than one.

## Edge / abuse

- Put a free CDN/WAF tier (e.g. Cloudflare) in front; cache `/` aggressively.
- `static/robots.txt` disallows `/api/` for honest crawlers.
- Rate limiting / request budget: decision pending the static-site evaluation
  — if the site goes fully static, the API (and this concern) disappears.

## Headers

CSP is generated by SvelteKit (`svelte.config.js`); other security headers are
set in `src/hooks.server.js`. If you add an external resource, update
`connect-src` or it will be blocked.
